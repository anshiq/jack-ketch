Problem and solution

Problems agents and you face

The problemHow jack-ketch solves it
1

Agents run the application in a shell and can read its output only after it has finished. If the shell is detached, all logs are lost and the port is orphaned.

One daemon per OS user owns every process. Logs are captured live into a searchable index and processes outlive agent sessions, so a later session re-attaches with list_processes instead of starting a duplicate.

2

In a typical workflow, your agent works while you keep the application running in a separate terminal for testing. After the agent finishes the implementation, you restart the application again, and if any error occurs, you manually copy and paste it back to get a solution.

The agent starts, restarts and watches the app itself. It reads the logs and the failure diagnosis directly, fixes the error and restarts, so nothing gets copy-pasted between terminal and chat.

3

Today, agents rely on unit tests to verify the application's implementation. Sometimes all methods pass their tests and behave correctly on their own, but an endpoint touches many methods and the pipeline can break at any point. The methods work correctly, yet their combination gives a wrong result and the endpoint responds incorrectly. This is skipped in almost every case, and the user ends up verifying this behaviour in production.

Since the application is running and accessible to the agent, the agent can simulate real requests and responses with probe alongside the unit tests, and see the log lines each request produced. Useful probes are saved as checks and re-run with run_checks.

4

To check endpoints, you have to manually paste curl commands that contain a secret token, which exposes it to the agents.

Test JWTs, cookies and API keys live encrypted in the web UI. The agent calls your API as a real user by profile name and never sees a value, which is scrubbed from every result and log.

5

It can't verify behaviour — did that endpoint really work, and what did the app log while serving it?

probe sends a request to the running app and returns the response plus the log lines it produced. Save the useful ones as checks and re-run them with run_checks.

Config that follows the project

Modes, ordered env and saved runs.

Apps are auto-detected and stored in the daemon database, not in your repository. Each app can run several ways. When a hand-built run works, jack-ketch asks you whether to save it as a mode.

project config · apps.apiYAML
{{ highlight `version: 3 apps: api: type: node workdir: ./services/api default_mode: dev env_sources: - file: .env - file: .env.local optional: true checks: - name: health url: /health modes: dev: command: [npm, run, dev] prod: command: [npm, start] env_sources: - vars: {NODE_ENV: production}` "yaml" "" }}
what the agent callsMCP
  1. start_process(app="api", mode="prod", timeout_ms=60000)starts the prod mode
  2. wait_for_log(process_id, ready=true)returns when the app says it is ready
  3. probe(process_id, url="/health")hits the running app and returns its logs too
  4. get_logs(process_id, stream="stderr", lines=100)reads the last 100 stderr lines
  5. run_checks(process_id)re-runs every saved check
  6. restart_process(process_id)restarts after a change
